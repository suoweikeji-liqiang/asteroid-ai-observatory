## 01. 封面 / 开场

东南亚的超级应用 Grab，有个数据仓库团队：上千个内部用户、一万五千多张表。随着平台变大，工程师每天被重复的支持工单淹没——查问题、修 SQL、答疑，做平台改进的时间越来越少。后来他们上了一套多 agent 系统，每个月省回几百个工程小时，把人从"救火"，挪向了"建平台"。


---

## 02. 这期看一个真在生产里跑的系统

我们讲过很多 agent 的理念，这一期不一样：它是一个真在生产环境里跑的多 agent 系统，由 InfoQ 报道、这家公司工程团队自己复盘。难得的，是它落地的那些设计决策。


---

## 03. 背景 · 被支持工单淹没

先看背景。这个数据平台是公司分析业务的核心地基。可用着用着，团队发现：相当大一部分精力，被重复的运维支持、和临时的排查给吃掉了，留给平台改进、系统设计的时间，越来越少。


---

## 04. 第一刀 · 把请求劈成两条线

他们动的第一刀，是把进来的请求，劈成两条工作流。


---

## 05. 调查线 与 增强线

所有进来的工程请求，被分成两类：一类叫调查，investigation；一类叫增强，enhancement。这一刀，是整套系统的骨架。


---

## 06. 调查线 · 只看不动手

调查线，专做诊断：分析查询、捞日志、查表结构、把问题总结清楚。它的特点是——只看、只查，不动手改任何东西。


---

## 07. 增强线 · 动手但要人审

增强线，专出可执行的东西：改代码、修 SQL、自动提一个待审核的合并请求。它动手，但产出，必须经过人审。


---

## 08. 为什么要这么劈

为什么这么劈？因为把"调查"和"动手改"分开之后，单个 agent 的推理复杂度立刻降了下来，生产里的可靠性，也明显上去了。一个 agent，别又想着诊断、又想着动手。


---

## 09. 第二刀 · 编排 + 专职 agent

第二刀，是怎么把这些 agent 协调起来。


---

## 10. 编排层

整套系统，用一个基于 LangGraph 的工作流引擎，再加上一层 FastAPI 服务，来协调三件事：请求路由、工具调用、还有跨 agent 的状态管理。


---

## 11. 先分类，再路由

一个请求进来，先被分类，再被路由给专门的 agent：有的负责上下文检索，有的负责代码搜索，有的负责生成方案。各管一段，不抢活。


---

## 12. 每个 agent，职责都收窄

这里有个关键：每个 agent 的职责，都被收得很窄。职责越窄，歧义越少，产出就越可预测。这跟我们讲长任务 harness、讲上线门禁，是同一条线——别让一个 agent 什么都干。


---

## 13. Supervisor · 调度中枢

在这些 agent 上面，还坐着一个主管，Supervisor。它专门管：agent 之间怎么通信、活儿怎么分派。它，就是这套多 agent 的调度中枢。


---

## 14. 第三刀 · 工具，从三十多个砍到一小撮

第三刀，砍在工具上——而这一刀，特别值得讲。


---

## 15. 工具一多，agent 就乱选

系统最早，暴露了三十多个内部工具：数据访问、日志、代码系统，全堆了上去。但很快就发现一个问题：工具一多，agent 选工具就开始乱选、变得不可预测。


---

## 16. 收敛成一小撮

于是他们做了个关键决定：把工具集，收敛成一小撮精挑细选过的。维护性立刻上来了，agent 乱选工具的毛病，也压了下去。这跟我们上一期讲 RL、讲 SDK 自带工具时的"少即是多"，是一个道理。


---

## 17. 留下来的，对着真实场景

那留下来的是哪些？受控的 SQL 执行、元数据访问、日志检索、还有接上 Git 的变更管理。每一类工具，都精确对着一条真实的支持场景，没有一个是摆设。


---

## 18. 第四刀 · 安全和上下文，才是真考验

前面是架构，接下来这两件，才是把它真正送进生产的考验：安全，和上下文。


---

## 19. 安全 · 是设计进去的

安全和治理，是一开始就设计进去的，不是事后补的：SQL 执行，有校验层兜着；敏感数据，有专门的检测和兜底；而所有会改代码的增强工作流，上线前，都必须有人来审——也就是 human-in-the-loop。这跟我们讲 Agent 安全、讲组织级治理，又接上了。


---

## 20. 上下文 · 真正的技术难点

而真正的技术难点，是上下文管理。多步的 agent 推理，要求在 token 的限制之内，一直维持住相关的状态——既不能忘，又不能塞爆。


---

## 21. 压缩 + 选择性检索

他们的解法，是结构化的上下文压缩，加上选择性的检索：让 agent 留住该留的信息，又不超出操作的上限。这一条，正好接回我们讲记忆、讲上下文层的那几期。


---

## 22. 第五刀 · 结果与启发

最后，看结果，和它留给我们的启发。


---

## 23. 结果 · 从救火到建平台

结果是：常见问题的解决周期变快了，花在重复支持上的时间降了下来。用那位分析负责人的话说——每个月省回几百个工程小时，工程精力，从被动的"救火"，挪向了更高价值的"建平台"。虽然他们没公开精确指标，但这个转变，是实打实的。


---

## 24. 启发一 · 先分解，别堆一个全能 agent

第一个启发：别想着造一个全能 agent。先把问题分解——按工作流分成调查和增强，按职责分成检索、搜索、生成，每一块都收窄。多 agent 的可靠性，恰恰来自这个"分"字。


---

## 25. 启发二 · 少工具 + 强治理

第二个启发：工具不是越多越好，要收敛到精挑的一小撮；而任何能改东西的动作，都得配上校验和人审。能力放开的同时，边界必须跟上。


---

## 26. 启发三 · 上下文决定上限

第三个启发，也是我们反复撞见的主线：多步 agent 的上限，卡在上下文管理上。压缩、选择性检索，不是锦上添花，而是它能不能在生产里跑稳的关键。
