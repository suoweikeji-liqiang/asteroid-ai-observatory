## 开场：长任务 Agent 为什么会跑偏

### hook_1

你有没有发现，让 AI 写一个小函数，常常很惊艳；但让它连续做一个完整应用，过一会儿就开始跑偏：忘记最初目标，绕开难题，自我感觉良好，最后交给你一堆看似完成、其实不敢上线的东西。

### hook_2

Anthropic 在二零二六年三月二十四日发布了一篇工程文章，题目是 Harness design for long-running application development。它真正值得看的地方，不是“Claude 又能做应用了”，而是它把长任务 Agent 拆成了一个可控制的工程系统。

### hook_3

这期的一句话结论是：多小时应用开发不能靠一个 prompt 硬撑，而要靠 planner、generator、evaluator、结构化交接和可验证标准。Agent 不是越自主越好，而是越能被管理、被评估、被恢复越好。

## 第一段：这篇文章表面讲什么

### s1_1

先把事实说清楚。Anthropic 这篇文章发表于二零二六年三月二十四日，作者说他们主要围绕两个问题展开：第一，让 Claude 生成高质量前端设计；第二，让 Claude 在无人干预下构建完整应用。

### s1_2

如果只当工具新闻看，你可能会得到一个很浅的结论：模型又进步了，应用可以自动生成了。但从工程角度看，它更像是在回答一个老问题：当任务长度从几分钟拉到几小时，系统到底靠什么不崩？

### s1_3

长任务失败通常不是突然爆炸，而是慢慢漂移。第一小时还在按需求走，第二小时开始为了通过局部测试绕路，第三小时忘了用户真正要什么，最后把“能运行”误当成“完成”。

### s1_4

所以这篇文章真正重要的词不是 autonomous，也不是 coding，而是 harness。中文可以理解成任务托架、运行约束、评估环境。它把模型放进一个有角色、有状态、有证据、有验收标准的结构里。

### s1_5

这里也要讲边界：这是一篇 Anthropic 自己的工程文章，不是第三方独立审计。我们可以学习它的架构判断，但不能把它讲成“长任务应用开发已经被完全自动化解决了”。

## 第二段：为什么一个 Agent 硬撑会跑偏

### s2_1

第一个坑是目标漂移。长任务里，Agent 会不断遇到局部选择：这个按钮怎么做、这个错误怎么绕、这个测试怎么过。每个选择单看都合理，但连起来可能已经离最初的产品目标很远。

### s2_2

第二个坑是上下文丢失。多小时任务里的需求、设计决策、失败尝试、环境状态，不可能只靠聊天记录自然保持。上下文一旦被压缩或替换，Agent 就很容易重新发明一遍错误方案。

### s2_3

第三个坑是自评偏差。让同一个 Agent 先写应用，再判断自己写得好不好，很容易变成自我合理化。它会解释为什么自己的方案可以接受，而不是严格寻找哪里不满足标准。

### s2_4

第四个坑更隐蔽：很多质量不是纯粹的单元测试能覆盖的。比如前端设计是不是清晰，信息层级是不是合理，交互是不是符合用户直觉。这些主观质量如果没有评分标准，就只能靠感觉。

### s2_5

所以长任务 Agent 的核心不是让模型一次想得更久，而是把“方向、产出、评估、交接”从模型内部拿出来，变成外部结构。外部结构越清楚，Agent 越不容易把局部成功误判成全局完成。

## 第三段：Planner、Generator、Evaluator 分别干什么

### s3_1

先看 planner。planner 的价值不是亲自写代码，而是把大目标拆成可执行块：下一步做什么，输入是什么，输出是什么，验收标准是什么，遇到失败要回到哪里。

### s3_2

generator 才是具体干活的角色。它写界面、改代码、产出文件、调用工具。它追求的是把 planner 给出的某个块做出来，而不是自己临时决定整条路线怎么变。

### s3_3

evaluator 的角色最容易被低估。它不是简单说“不错”，而是拿着明确标准去挑错：设计是否达标，功能是否满足，约束有没有违反，证据是否足够，下一轮应该修哪里。

### s3_4

为什么要分开？因为作者和裁判不能完全是同一个人。内容生产也是一样：写稿的人如果同时当最终事实核查和质量门禁，最容易把自己的表达合理化。工程任务里也是如此。

### s3_5

当然，三角色架构不是唯一解。你可以用更多角色，也可以把某些角色合并。但底层原则是稳定的：规划、生成、评估必须在流程上可区分，在证据上可追踪。

## 第四段：structured artifacts 为什么比聊天记录重要

### s4_1

长任务里，聊天记录不是一个好的状态源。它太长、太散、太容易混入试错过程。真正能交接的是 artifact：计划、任务列表、接口约束、设计标准、测试结果、风险记录。

### s4_2

一旦任务跨 session，问题就更明显。新的执行者不应该靠读几万字聊天猜测当前状态，而应该看到一份清楚的交接物：已经做了什么，为什么这么做，哪些方案失败了，下一步验收什么。

### s4_3

artifact 还有一个好处：它能防止错误反复发生。比如某个方案已经被证明不可行，如果只留在聊天里，后续 Agent 很可能重新踩坑；如果写进 decision log，它就会成为约束。

### s4_4

这和内容生产线完全同理。source brief、outline、draft、review notes、factcheck、publish pack，这些都不是形式主义，而是让下一轮作者、编辑、事实核查能接得住。

### s4_5

最小动作很简单：以后任何超过三十分钟的 Agent 任务，都强制生成三份 artifact：任务计划、决策记录、验收结果。没有这三份，就不要说任务真的完成了。

## 第五段：普通团队怎么做小号 P-G-E

### s5_1

普通团队第一步，不是立刻搭三个 Agent，而是把任务块写清楚。每个块至少有四个字段：输入、输出、验收标准、失败时怎么回滚。没有验收标准的任务，不适合交给长任务 Agent。

### s5_2

第二步，生成和评估分开。写代码、写稿、写方案的人可以是一个 Agent；但最后做事实核查、测试复核、风格评分的，最好换一个上下文，甚至换一个模型或规则脚本。

### s5_3

第三步，把主观质量写成评分标准。比如内容稿可以评结构、证据、节奏、受众、风险；前端设计可以评层级、对比、可读性、反馈和一致性。不要只说“感觉不够好”。

### s5_4

第四步，强制证据包。代码任务要有改动摘要、测试结果、截图、风险和回滚方式；内容任务要有来源链接、事实风险表、人工确认项和发布边界。

### s5_5

第五步，先低风险。不要一上来让 Agent 全自动改核心系统。先从调研、草稿、小修、小重构、只读诊断开始。等计划、产出、评估和交接跑顺，再逐步扩权。

### s5_6

放到我的场景里，日报和工程博客线可以拆成 planner、writer、factchecker、editor；develop_os 里的 Requirement Unit 和 Stability，可以成为 planner 和 evaluator 的结构化对象；智能运维诊断，也应该先规划检查路径，再执行查询，最后复核结论。

## 结尾：Agent 工程化的真正分水岭

### close_1

所以这期的结论很简单：长任务 Agent 的分水岭，不是能不能连续输出更多字，而是有没有一套能承载长任务的 harness。没有 planner，就容易失去方向；没有 evaluator，就容易自我合理化；没有 artifacts，就无法交接和复盘。

### close_2

也不要神化。Anthropic 这篇文章提供的是一种工程实践，不是唯一答案，更不是“以后应用开发不需要人了”。越长、越复杂、越接近生产的任务，越需要明确的人类审核和上线门禁。

### close_3

如果你今天就想用起来，先做一个小动作：给下一个超过三十分钟的 Agent 任务，写一份计划，一份决策记录，一份验收结果。然后让另一个 evaluator 按标准复核。先把这个小闭环跑稳，再谈多小时全自动。

### close_4

Agent 不是越自主越好，而是越可控越好。真正能进入团队流程的，不是会聊天的模型，而是能被计划、被观察、被评估、被恢复的工作系统。
