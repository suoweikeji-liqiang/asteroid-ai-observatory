## 01. 封面

硅谷现在流行一个玩法：把 AI 派出去替你写代码。你丢一个任务给它，关上电脑走人，它自己在云端把活干完、回你一个 PR。听着很爽。但我一个本地 Codex、ZCode、反重力 一堆工具换着用的人，看完这波云委派潮，第一反应是先按住、不追。这期不做横评，我把"云 agent"这个被炒烂的词拆开，给你看清楚它到底卖的是什么、你到底用不用得上、什么时候才真该用。


---

## 02. 开场先判

先把结论摊开。这期最大的坑，是很多人把"能用手机发任务"当成了"用上云 agent"——这俩根本不是一回事。第一，云 agent 真正的好处，不是"AI 会写代码"，本地早就会了；它卖的是并行、隔离沙箱、和零运维这层东西。第二，手机、甚至微信飞书发任务，现在已经是全行业标配，国产在这块还更领先，根本不用羡慕。第三，也最扎心：海外那几家国内大半够不到，但你要的好处，要么国产已经端上桌，要么能用自己的机器平替。往下我一个个拆。


---

## 03. 云 agent 是什么

先说清楚它到底是什么。以 GitHub 的 Copilot 云 agent 为例，官方文档写得很直白：你把一个 Issue、或者一句话丢给它，它就在一个云端隔离环境里自己读代码库、定计划、改分支、跑测试，最后提一个 Pull Request。这条赛道的选手不少：Devin 是鼻祖，还有 Codex Cloud、Claude Code 网页版、Copilot coding agent、谷歌 Jules、Cursor 云端 agent。注意一个变化：工作单位变了——不再是逐行帮你补全，而是"一个任务，换一份能合并的 PR"，你的角色从写代码，变成审 PR。


---

## 04. 三根轴

但别被"云 agent"这个词骗了，它把三件不同的事糊成了一坨。我给你拆成三根轴。第一根，在哪跑——活是在你自己的机器上跑，还是在人家托管的云沙箱里跑。第二根，谁在盯——你实时盯着、一步步引导，还是丢出去让它自己异步跑完。第三根，从哪控——你在桌面前操作，还是用手机、微信、飞书远程发起。把这三根轴分开，你就看明白了：所谓"云 agent"，其实就是"云托管"加"异步委派"打了个包；而"手机、IM 发任务"，只动了第三根轴。


---

## 05. 手机/IM 发任务 ≠ 云 agent

这里得澄清一个最常见的误会：很多人以为，能用手机把任务甩出去，就等于用上云 agent 了。不是。手机发任务，现在是全行业标配——Codex 的手机 App、Claude 的手机端都能发，国产的通义、Trae、腾讯 CodeBuddy 也都能从手机派活；智谱新出的 ZCode 更狠，直接在微信、飞书群里 @ 它一句话，任务就跑起来了。换句话说，"能用手机、甚至能用微信飞书控制"这件事，根本不是云 agent 的独门绝技——它是所有人的标配，国产在这块还更接地气。云 agent 真正独占、别人难复刻的，从头到尾只有一样：托管的一次性隔离沙箱，加零运维的并行。


---

## 06. 国内能不能用

那国内到底能不能用？老实说，海外这几家对国内基本不友好。我给你数几个硬门槛：几乎全部都绑 GitHub，云虚拟机又在海外，Devin、Jules、Codex 这些不挂梯子基本够不到；付费还得外卡。更直接的是 Claude 这一系——它的云端版对大陆 IP 是区域封锁的，得挂梯子、还不稳，付费也不保证进得去，这不是封号风险，是访问层面就卡你。最后一道是合规——你的私有仓库代码，要整个上传到海外的云沙箱里，国内公司这关基本就过不去。


---

## 07. 国内平替

用不上，不代表你要的好处拿不到。看你想要哪一样，都有能落地的平替。你只想要"手机、甚至微信飞书发任务"——这个国产工具原生就给你了：智谱 ZCode 从微信飞书 @ 发任务，腾讯 CodeBuddy 用企业微信绑定派活，通义、Trae 也都有手机端；想更彻底自己掌控的，再上手机 SSH 连自己的机器加 Tailscale 那套极客方案。你想要"甩出去异步委派"——用 GitHub 或者国内的 Gitea 的 Actions，由 Issue 触发 aider 或者 Claude Code 的 headless 模式，改完自动提 PR，这就是自己搭的委派 agent；我之前专门做过一期常驻 Agent OS，OpenClaw、Hermes 那一挂，正好能挂着接这种任务。你想要"并行加隔离"——git worktree 开多个分支、多个 tmux 窗口手动并行，Docker 起隔离环境当沙箱。只有当你真的懒得自己搭环境、又要一次并行几十个任务，那才轮到花钱上云。


---

## 08. 订了会员的人：什么活该甩给云端

那反过来说，如果你已经订了 Codex、Cursor，也能正常用，什么时候真该切到云端委派？记住：云端不是来替代本地的，是补位的，挑对活才值。四种活适合甩出去：第一，一堆互不相干的小杂活——改文档、批量加测试、升个依赖、清一波 lint——甩五个并行，别一个个盯。第二，边界清楚、验收明确的活，你一句话能说清要什么、怎么算做完。第三，要装一堆脏依赖、或想在陌生分支上做破坏性实验——用云端一次性沙箱，别弄脏本机。第四，你人不在电脑前——通勤、开会、睡觉，手机甩个任务出去，回来审 PR。反过来，四种活留在本地：需求不清、要边做边聊的探索活；要你实时盯着、随时打断纠偏的活；不能外传的敏感代码；还有小项目快速迭代，你就坐在电脑前，绕云端一圈纯属折腾。一句话记：要过程、要控制的活自己上；只要结果、边界清、能并行的活甩出去。就像你不会盯着实习生做每件小事，但核心逻辑，你还是亲手雕。


---

## 09. 立场收尾

所以回到最开始：这波云委派潮，我为什么先按住不追。不是它没用——用对场景，它真能帮你清 backlog；是因为它被吹得像"AI 全自动开发"的银弹，可它真正独占的，其实只有"帮你把环境和并行运维了"这一小块。手机、IM 发任务国产早标配了，异步和并行你自己也搭得起来。所以别被这个包装得很未来的词唬住：够得到、又要并行几十个任务的，用；够不到的，自建或用国产平替；图省事的个人开发者，本地加一个手机入口就够了。挑对场景，别乱掏钱。
