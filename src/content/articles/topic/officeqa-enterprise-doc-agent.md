## 主题

别再说 RAG 简单了：OfficeQA Pro 暴露企业文档 Agent 真实门槛

## 开场：企业知识库最容易被低估的坑

### hook_step_1_p1

如果你也做过企业知识库，大概率听过这句话：把文档丢进向量库，再接一个聊天框，不就能问了吗？但 Databricks 最近拿出来的 OfficeQA Pro，正好把这个想法打醒。

### hook_step_1_p2

它测的不是干净网页，也不是几段说明书，而是扫描 PDF、历史文件、长文档、密集表格和跨文档数字推理。

### hook_step_1_p3

也就是说，这期我们不聊“某个模型又刷榜了”，我们聊一个更现实的问题：为什么企业文档 Agent，远比一个 RAG demo 难。

## 第一段：这个案例到底是什么

### signal_01_step_1_p1

今天这个案例，主角不是 Databricks 这个名字本身，而是它和 OpenAI 一起提到的 OfficeQA Pro。

### signal_01_step_1_p2

你可以把它理解成一个专门折磨企业文档 Agent 的测试集：系统要面对历史财政公报、扫描页、长文档、复杂表格，然后回答需要证据支撑的问题。

### signal_01_step_1_p3

它要测的不是“能不能说得像”，而是能不能从文档里找对、抽对、算对，并且给出 grounded answer，也就是有依据的答案。

### signal_01_step_2_p1

几个关键数字要先说清楚。

### signal_01_step_2_p2

OpenAI 的客户故事里称，GPT-5.5 在 Databricks 的 OfficeQA Pro 上超过 50% accuracy，并且相比 GPT-5.4 错误减少 46%。

### signal_01_step_2_p3

论文和仓库那边则给了测试集背景：OfficeQA Pro 使用美国财政部历史公报，大约八万九千页，超过两千六百万个数值，Pro 集合是一百三十三个问题。

### signal_01_step_2_p4

这里我会特别强调：这些数字是官方页面、论文和项目仓库里的口径，不是我做的第三方复测。

### signal_01_step_3_p1

所以这条新闻如果只看成 GPT-5.5 又刷了一个榜，就太浅了。真正值得看的，是一个反差：超过 50% 是进步，但也说明真实企业文档任务还远没到“放心全自动”的程度。

### signal_01_step_3_p2

对做 Agent 的团队来说，这个数字更像一盏警示灯：企业文档不是问答题，而是一条长链路，链路上任何一步错，最后答案都可能错得很自信。

## 第二段：第一道坎不是检索，是解析

### signal_02_step_1_p1

第一道坎其实不是向量检索，而是解析。很多企业文档不是干净的 markdown，它可能是十几年前的 PDF，里面有扫描页，有歪掉的表格，有跨页标题，有脚注，有单位，有合并单元格。

### signal_02_step_1_p2

你把它变成文本的那一刻，就已经在做一次高风险转换。只要这里把一个数字、一个年份、一个列名抽错，后面的模型再聪明，也是在错误材料上推理。

### signal_02_step_2_p1

这也是为什么很多知识库 demo 看起来很顺。你拿几篇干净文档问“某个概念是什么”，模型当然能答。但真实企业里，问题经常是：二零一二年到二零一六年，哪个指标变化最大？

### signal_02_step_2_p2

这个变化来自哪几份文件？中间有没有口径调整？这种问题一出来，系统就不能只靠语义相似度，它必须理解表格结构、时间范围、单位和计算关系。

### signal_02_step_3_p1

所以普通团队如果要做企业文档 Agent，第一步不是急着换更强模型，而是先做解析验收。

### signal_02_step_3_p2

随便抽二十份最脏的历史文件，检查 OCR 准不准、表格能不能还原、数字有没有单位、页码和来源能不能保留。

### signal_02_step_3_p3

你会发现，很多所谓 RAG 效果差，根本不是检索差，而是文档在进系统的第一天就已经坏了。

## 第三段：RAG 不是召回一段话就结束

### signal_03_step_1_p1

OfficeQA Pro 让我觉得最有价值的地方，是它把企业文档任务重新拆成四段：parsing，retrieval，reasoning，answer verification。

### signal_03_step_1_p2

中文说就是：先把文档解析成可用结构，再找对资料，再根据资料推理，最后验证答案和证据是否对得上。RAG 只是中间一段，不是整个系统。

### signal_03_step_2_p1

这个拆法对工程团队很重要。因为当系统答错时，你不能只说“模型幻觉了”。你要能定位：是 OCR 把数字识别错了？是检索漏掉了关键年份？是模型抽错了表格列？还是计算过程出了错？

### signal_03_step_2_p2

如果没有这种分段观测，你就只能不断换模型、换 embedding、换 prompt，最后还是不知道问题到底在哪里。

### signal_03_step_3_p1

还有一点很关键：证据不是答案后面贴一个链接装饰一下。企业场景里，证据应该包括文件名、页码、表格位置、抽取字段、计算过程，必要时还要保留原图或原表。

### signal_03_step_3_p2

只有这样，人类审核者才能判断这个答案是否能进报告、进合同、进决策。没有证据链的企业知识库，本质上还是一个会说话的黑盒。

## 第四段：评测不是排行榜，是上线门禁

### signal_04_step_1_p1

OpenAI 原文称 GPT-5.5 在 OfficeQA Pro 上超过 50% accuracy。

### signal_04_step_1_p2

这个数字很容易被写成“企业文档 Agent 快解决了”，但我更愿意反过来看：如果这么强的模型在这个任务上也只是刚过一半，那说明企业文档问答的工程门槛非常高。它不是一个换模型就能跳过的问题。

### signal_04_step_2_p1

对普通团队来说，benchmark 最大的启发不是去追 OfficeQA Pro 分数，而是学它的评测思想。

### signal_04_step_2_p2

你要给自己的知识库建立一组真实任务：不是问“报销制度是什么”，而是问“去年第三季度某类费用环比变化多少，依据是哪张表”。每个问题都要有标准答案、证据位置和可接受误差。只有过了这些题，Agent 才能进入更高风险的工作流。

### signal_04_step_3_p1

这也是我一直强调的路线：不要一上来做全自动企业知识库。先选低风险、边界清楚、验收明确的任务，比如内部资料检索、报告初稿、数据核对提示。让 Agent 给建议，人来确认。

### signal_04_step_3_p2

等解析、检索、证据和人工审核都跑顺了，再逐步扩大范围。真正成熟的企业 Agent，是从可控小闭环长出来的。

## 第五段：普通团队怎么复用

### signal_05_step_1_p1

如果你现在手上就有一个企业知识库项目，我建议先做一个小号 OfficeQA。不要从几千份文档开始，先挑三十到五十份最常用、最麻烦、最脏的文档。

### signal_05_step_1_p2

然后让业务同事写二十个真实问题：最好有跨文件、有表格、有年份、有单位、有计算。这个任务集，就是你自己的上线门禁。

### signal_05_step_2_p1

接下来，不要只看最终答案对不对。要分段打分：解析有没有保留结构，检索有没有找到关键页，抽取字段对不对，推理过程能不能复现，答案有没有证据。这样你才知道系统短板在哪里。

### signal_05_step_2_p2

不然你今天换模型好一点，明天换一批文档还是会崩，问题没法积累成工程资产。

### signal_05_step_3_p1

这件事跟我们自己的场景也很近。比如售前助手要读历史方案、报价单、图纸、测点表；运维报告助手要读周报、月报、巡检记录；内容生产线要追踪来源、口径和证据。

### signal_05_step_3_p2

它们共同的底层问题都是：知识不能只是一段文本，还要带来源、结构、适用范围和验证方式。

## 结尾：企业知识库的下半场

### signal_close_step_1_p1

所以这一期的结论很简单：企业知识库的下半场，不是换一个更大的向量库，也不是再包一层更会聊天的界面，而是把文档解析、检索、推理、验证和权限治理，做成一套可观察、可追溯、可验收的工程系统。

### signal_close_step_1_p2

OfficeQA Pro 真正提醒我们的，是不要被 RAG demo 的顺滑感骗了。企业文档会把每一个脆弱环节都放大。

### signal_close_step_2_p1

如果你正在做企业知识库，今天可以先做一个很小的动作：拿出二十道真实业务题，每道题都写清楚标准答案、来源页码、表格位置和计算过程。先别急着问模型多聪明，先问系统能不能稳定通过这些门禁。

### signal_close_step_2_p2

能过，才谈扩权；过不了，就先回去修解析、检索和证据链。
