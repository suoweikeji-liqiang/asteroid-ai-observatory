## 01. 封面 / 开场

二零二五年，AI 写代码这件事悄悄变了味。它从"帮你补全下一行"，变成了"写完整个改动、跑完单元测试、再自己开下一个"。这套打法有了个名字，叫 agentic coding。到二六年中，很多大公司都至少在跑一条这样的流水线。但麻烦也来了：那些在小项目上很灵的技巧，一旦对准一个两千个仓库、堆了十二年的巨型代码库，立刻就垮。


---

## 02. 它在 80% 处悄悄崩

而且崩得很有特点：agent 能稳稳地做完一个任务里看得见的那 80%，却悄悄漏掉看不见的那 20%。这一期就讲清楚一件事——这 20% 的漏，几乎从来不是模型不够聪明，而是上下文基础设施的问题。


---

## 03. 核心判断 · 天花板是上下文

所以这期的核心判断很直接：agentic coding 的生产力天花板，是由上下文决定的，不是由模型质量决定的。模型大家都差不多，真正拉开差距的，是你给 agent 配了一套什么样的"代码库视野"。


---

## 04. 第一部分 · 先把概念分清

先把几个被混在一起的概念分清楚。


---

## 05. 什么是 agentic coding

agentic coding，是让一个自主的 AI agent 去规划、写、测、再迭代代码，靠一套工具——一个 shell、一个测试运行器、代码搜索、还有版本控制——把一个复杂任务跑完。你不再一行行敲、一条条接受建议，而是描述一个目标，让它跑一个循环，直到达成、或者卡住。


---

## 06. 和补全、对话的区别

它和别的 AI 编程的分界线，是自主使用工具。自动补全，预测下一个词；对话，回答你贴进去的问题；而 agent 会真的动手：读文件、调工具、跑命令、看输出，再自己决定下一步——和一个人类工程师的方式一样。


---

## 07. 第二部分 · 它不是 vibe coding

这里要泼一盆冷水：agentic coding，不是 vibe coding。


---

## 08. 区别在"谁对结果负责"

vibe coding 是一种姿态：信模型、不读 diff、一直催到它能跑为止——它最早是用来形容那种扔掉就算的周末项目的。而 agentic coding 是一种架构：模型接上工具、跑在循环里，产出的代码要由一个人对着"完成的定义"去审。区别就在于：谁对"对不对"负责。vibe coding 在出错代价为零时才成立；agentic coding 必须在出错代价是一次线上事故时还成立。


---

## 09. 进了别人维护的库，你就在做

所以有一条很硬的判断：只要你的代码，是合进一个别人也在维护的代码库，那你就是在做 agentic coding，不管你叫不叫它这个名字。把 agent 的产出当成"需要被审的代码"，而不是"一个成品"——这就是那条线。


---

## 10. 第三部分 · 这个循环怎么转

那这个循环，到底怎么转？


---

## 11. 七步一个圈

几乎每套 agentic coding 系统，跑的都是同一个圈：第一步，提示，你说清目标；第二步，搜集上下文，它搜代码库、读文件、拉文档和工单；第三步，规划，列出一串改动和验证；第四步，执行，写代码、改配置、调工具；第五步，测试，跑测试、跑检查；第六步，修正，失败作为新观察喂回去，再来一圈；最后，输出一个 diff 给你审。


---

## 12. 差异在循环，不在模型

让一个 agent 比另一个强的，很少是模型本身——很多工具用的是同一批前沿模型。真正的差异，在模型周围那套系统：检索、工具使用、规划、沙盒、评审。而其中变化最大、最决定成败的，是第二步——搜集上下文。


---

## 13. 模型只能推理它看得见的

为什么第二步最关键？因为模型只能对它看得见的代码做推理。如果 agent 搜了一下本地目录、找到三个相关文件，它就照着这三个文件去规划。可真实的改动要是涉及九个仓库里的十七个文件，它不知道，也不会主动问。结果它写出一段自信、而且在局部看完全正确的代码——却漏掉了三分之二的活。


---

## 14. 近似检索 vs 确定性检索

这就引出一个关键区别：近似检索，和确定性检索。近似检索，是向量相似度、是"看起来相关的文件"；确定性检索，是精确的符号引用——每一个调用点、每一个接口实现。在小仓库上，近似检索够用。可到了大代码库，近似检索只会返回一堆"看着挺像"的结果，漏掉横切的影响，于是 agent 就交出一段"看着挺对"、却埋着隐患的代码。这一点，和我们在 RAG 那几期讲的是同一个道理。


---

## 15. 第四部分 · 80% 问题

讲到这，就能说清那个真正的痛点了——80% 问题。


---

## 16. 三天后，别人的 CI 红了

场景是这样：agent 五分钟做完一个任务，diff 看着很干净，测试也过了，你就合了。三天后，另一个团队的 CI 突然开始报错——因为一个下游服务，还在等着那个旧的函数签名，而你的 agent，根本不知道那个服务存在。


---

## 17. 漏的，总是同几类

更要命的是，它漏的东西总是同几类：包在被改函数外面的鉴权中间件、在另一层做序列化的接口数据结构、记录状态变更的审计日志、躺在兄弟仓库里的集成测试、镜像后端权限的前端守卫，还有那些需要重新生成的迁移脚本。看得见的它都做了，看不见的它全漏了。


---

## 18. 不是模型变笨，是多了眼睛

但请注意：这不是模型变笨了。给同一个 agent 一套跨仓库的搜索，同样这个任务，多层的引用一下子全浮现出来，它就会去改那些本来会漏掉的文件。用原文一句很妙的话说——agent 没有变聪明，它只是多了几双眼睛。


---

## 19. 越能干，反而搜得越多

这里还有个反直觉的现象：原文里说，八成多的大企业账户，在 AI 铺开之后，代码行数是稳步上涨的；而开发们的反应，是搜得更多，不是更少。因为 agent 的产能上限，就卡在它能看见多少——在大代码库上，它默认能看见的，只是一个碎片。


---

## 20. 三种表现，别 debug 错层

80% 问题，会以三种方式冒出来：一是横切改动，任何牵动多个服务、仓库或层次的活；二是隐藏的技术债，那些它从不会打开的自定义装饰器、兄弟微服务；三是 monorepo 盲区，搜索被困在当前目录、看不见整棵树。如果你团队正撞上这些、却在怪模型——那你是在 debug 错误的那一层。


---

## 21. 第五部分 · 引擎、线路、燃料

那解药是什么？原文给了一个特别好记的心智模型。


---

## 22. 好引擎，加坏油也熄火

这个模型是：agent 是引擎，MCP 是线路，而代码库的上下文，是燃料。一台再好的引擎，加上劣质的燃料，照样熄火。所以如果 80% 问题是个上下文问题，那解决它的办法，就是给每一个 agent，配上一个资深工程师干到第一千天才有的那种代码库视野。


---

## 23. 一套有纪律的工作流

而真正用好 agentic coding 的团队，靠的不是最贵的模型，是一套有纪律的工作流：资深工程师来定任务范围、写验收标准；给 agent 接上代码搜索、内部文档、工单；让它跑循环；然后，像审一个人类的 PR 一样去审它的 diff——读它、在本地跑它；再用 CI 当门禁，agent 的提交也得过人类提交那同一套检查；最后做事后审计，把 agent 当成一个有提交权限的外包来管。


---

## 24. 第六部分 · 落到你自己的盘子里

这套东西，落到我们自己的活儿上，有两点很值得记。


---

## 25. 开发者的角色，上移了一层

第一点：开发者的角色变了。少敲代码，多做的是"掌舵"和"验收"——同时盯着好几个并发的 agent 跑。活没有消失，它只是上移了一层。这里有个很实用的小动作：当一个 agent 说"我做完了"，你就去代码库里搜一下它碰过的那些符号，看还有没有别处用到；只要冒出一处它从没打开过的，那这个任务，就还没做完。


---

## 26. 第二点 · 把力气投到上下文上

第二点，也是这一整期的落点：既然天花板是上下文、不是模型，那就先选一个你团队信得过的 agent，然后把同样多的力气，投到那层给它完整代码库视野的基础设施上。这也接回我们前面讲过的主线——能让 agent 直接读到可信的、结构化的上下文，用确定性的搜索，而不是退回去赌近似的向量相似。省下来的力气，就该花在这里。
