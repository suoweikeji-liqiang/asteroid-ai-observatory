# 完整口播稿：从 AutoGPT 到 AgentOS，Agent 技术到底在进化什么？

> 建议时长：11-14 分钟  
> 视频定位：专业技术专题，不做工具教程，不做简单框架横评。  
> 讲法原则：中文概念优先，英文名只作为索引；重点讲清楚技术责任如何一层层被拆出来。

---

## 00. 开场：别急着问哪个框架最强


这几年，Agent 框架变得特别快。

2023 年，大家还在看 AutoGPT、BabyAGI，觉得大模型终于能自己干活了。  
2024 年，LangGraph、AutoGen、CrewAI 开始火，大家开始讨论流程、状态、多智能体协作。  
2025 年以后，MCP、OpenAI Agents SDK、Google ADK、AgentScope、Agno 这些东西又陆续出现，开始讲工具协议、记忆、技能、运行时、控制平面，甚至 AgentOS。

如果只看名字，会觉得特别乱。

今天一个框架，明天一个开发套件，后天又冒出来一个智能体操作系统。很多人第一反应是：到底该选哪个？哪个会成为最终答案？

但这个问题不能只从“框架排名”看。

更值得问的是：**为什么这些框架会一层一层长出来？**

核心判断是：Agent 技术的演进，不是功能越来越多的历史，而是大模型从“会回答”走向“会做事”以后，提示词扛不住的系统责任，被一层层拆出来的历史。

以前我们写一句提示词，让模型回答问题就够了。  
但当我们希望它真的去查资料、调用工具、写代码、改文件、处理工单、做诊断，问题就变了。

它要知道任务走到哪一步。  
它要知道哪些信息该记住。  
它要知道哪些动作危险，不能直接执行。  
它要能把一类任务的方法沉淀下来，下次复用。  
它出错以后，要能被追踪、回放、评估和纠正。

这时，Agent 就不再是一个“聪明的聊天机器人”，而变成一个需要工程架构支撑的长期执行系统。

所以这条主线采用“技术责任递进”的方式看这几年 Agent 框架的变化。

这条线大概是：

**自动循环 → 流程与状态 → 记忆与知识 → 技能沉淀 → 工具协议 → 多角色协作 → 运行时和控制平面。**

抓住这条线，再去看 AutoGPT、LangGraph、CrewAI、AgentScope、Agno、OpenAI Agents SDK、Google ADK，就不会被名字带着跑。

## 01. 2023：AutoGPT 时代，第一次看到“自动循环”


第一阶段，可以用 AutoGPT 和 BabyAGI 代表。

那个时候最震撼的地方是：大模型好像不只是回答问题，而是可以围绕一个目标自己往前推进。

它的基本模式很简单：

用户给一个目标。  
模型先规划下一步。  
然后调用工具。  
拿到结果以后观察。  
再决定下一步。

这就是早期 Agent Loop。为了少用英文，我们直接叫它：**自动执行循环**。

也就是：**目标输入 → 计划一步 → 执行一步 → 看结果 → 再计划一步。**

这件事很有想象力。因为它让人第一次直观感受到，大模型可能不只是一个问答系统，而是一个可以围绕目标行动的执行器。

但问题也很快暴露出来。

第一个问题是：没有稳定状态。

它可能知道自己上一轮说了什么，但它不一定可靠地知道整个任务现在走到哪一步。哪些分支已经试过，哪些结论已经被否定，哪些动作等待人工确认，这些都很容易混在上下文里。

第二个问题是：没有强边界。

当 Agent 只是说错一句话，风险还比较可控。可一旦它连接浏览器、文件、命令行、数据库，错误就可能变成真实操作。

第三个问题是：没有可靠复盘。

最后它给你一个结果，看起来像样，但中间为什么这样判断，调用了什么工具，哪一步出错，哪里被幻觉带偏，系统很难回放。

所以 AutoGPT 这类早期 Agent 最大的贡献，不是给出了成熟生产架构，而是把行业真正的问题暴露出来了：

**如果让大模型自己循环执行，我们到底需要哪些工程约束？**

这个问题，直接把行业推向下一阶段：流程与状态。

## 02. 流程与状态：Agent 从自由循环，变成可设计的任务系统


第二阶段，可以用 LangGraph 代表“流程与状态”这条路线。

先把两个词说清楚。

Workflow，就是工作流，解决的是“步骤怎么走”。  
State，就是状态，解决的是“任务走到哪一步”。

早期 Agent 最大的问题之一，是它看起来在行动，但工程系统不知道它到底处在什么状态。

LangGraph 这类路线的关键思路是：不要把所有东西都塞进一段提示词，也不要只靠一个模型自由循环，而是把任务拆成图。

图里面有节点，有分支，有共享状态，有检查点，也可以在关键位置暂停，等人确认以后再继续。

这一步非常重要。

因为真实任务往往不是一次问答。比如代码修改、资料研究、客户工单处理、设备诊断、合同审核，这些任务中间都可能需要：

保存当前进度；  
工具失败后重试；  
根据结果走不同分支；  
等待人工确认；  
任务中断后恢复；  
出问题以后回看当时为什么这样走。

这就是流程和状态的意义。

所以 LangGraph 的价值，不只是“它也能写 Agent”。它真正代表的拐点是：

**Agent 从不可控的自动循环，开始变成可以被设计、暂停、恢复和接管的状态机。**

2023 年大家问的是：AI 能不能自己干活？  
2024 年真正的问题变成了：AI 干活的时候，系统能不能知道它走到哪一步？

这就是第一层工程化。

但只有流程和状态还不够。因为一个长期执行系统，不能每次都像失忆一样从零开始。

于是第三层出现了：记忆与知识。

## 03. 记忆与知识：不是把聊天记录全存起来


Agent 的记忆经常被讲得太简单。很多人一说记忆，马上想到“保存聊天记录”或者“接一个向量库”。

但真正专业地看，记忆至少要分成四类。

第一类，是短期状态记忆。

它不是为了让 AI 显得更懂你，而是为了让任务不中断。比如当前任务做到哪一步，已经尝试过哪些工具，哪些结论被否定，下一步等谁确认。

这类记忆更接近“任务状态”。它和工作流、检查点关系很近。

第二类，是长期用户或业务记忆。

比如用户偏好、项目背景、公司规则、某个客户的特殊约束。这类信息跨会话存在，可以让系统下次不再从零理解。

但这类记忆也最危险。因为它涉及隐私、权限、过期信息和错误归因。系统不能什么都记，也不能永远记。

第三类，是知识库或检索增强。

也就是大家常说的 RAG。它的本质是：从文档、数据库、网页、代码库里检索相关信息，再交给模型使用。

需要强调一点：知识库不是记忆的全部。它更像外部资料入口。系统能查到资料，不等于它真的学会了怎么做事。

第四类，是学习型记忆。

这就更进一步了。系统不只是存信息，而是把失败案例、用户反馈、评估结果整理出来，再反过来改进后续行为。

你会发现，Agno 讲 Learning Machines，Claude、Agno、AgentScope 这些体系都在讲 Skills、Memory、Long-Term Memory，本质上都在靠近同一个方向：

**Agent 不应该每轮都临时发挥，而应该有可积累、可治理、可复用的经验层。**

所以，记忆这一层真正要解决的不是“多存一点上下文”，而是：

**系统应该记住什么？记多久？谁能看？什么时候失效？错了怎么纠正？怎么从记忆变成能力？**

如果没有这些治理，长期记忆会从智能增强，变成错误放大器。

比如一次错误诊断被系统记住，下次又被当成经验调用；  
比如用户一次临时偏好被永久保存，后面所有任务都被带偏；  
比如过期文档还在知识库里，模型检索到了以后一本正经地引用。

这就是为什么记忆不能只靠“存起来”。

记忆之后，下一层就是技能。

## 04. 技能：从“提示词复用”到“能力沉淀”


Skill 可以直接理解成“技能包”。

这个词很关键，因为它代表一个变化：Agent 系统不再只靠临时提示词，而开始把一类任务的做法封装起来。

什么是技能包？

它不是一句提示词，也不只是一个工具接口。

一个真正的技能包，通常包含：

做这类任务的步骤；  
判断标准；  
模板和示例；  
需要调用的工具或代码；  
容易出错的地方；  
输出格式；  
甚至测试和验收方式。

比如“代码评审技能”，不是一句“帮我评审代码”。它应该知道评审哪些维度，如何检查边界条件，如何看测试，如何判断风险，如何输出修改建议。

比如“故障诊断技能”，也不是一句“分析故障原因”。它应该知道先看哪些数据，如何排除传感器异常，如何查历史工况，如何组织证据链，什么时候需要人工确认。

这就是技能包和提示词的区别。

提示词更像一次性指令。  
技能包更像可复用的方法资产。

未来真正值钱的不一定是框架本身，而是技能沉淀。

框架会变，模型会变，但一个组织把自己的业务经验、流程模板、检查标准、工具调用方式沉淀成技能包，这个东西会越来越值钱。

Claude Skills 把技能描述成可复用的、按需加载的资源，用来提供特定领域的工作流、上下文和最佳实践。Agno 也在讲 Agent Skills 和 Learning Machines。AgentScope 文档里也出现 Agent Skill。

这说明“技能”不是某一家框架的噱头，而是行业正在共同靠近的方向。

更通俗地说：

**工具让 Agent 能做动作，记忆让 Agent 知道上下文，技能让 Agent 知道这类事情应该怎么做。**

如果没有技能层，Agent 每次都像一个聪明但没经验的实习生。你要不断告诉它背景、标准、模板、注意事项。

有了技能层，才有可能把高手经验变成团队能力。

但技能要真正工作，还需要连接外部工具和数据。于是下一层就是工具协议。

## 05. 工具协议：MCP 解决连接，但不等于安全边界


MCP 这几年很火。

它的核心可以说得很简单：

**让 AI 应用用更统一的方式连接外部工具、数据源和系统。**

在 MCP 之前，每个 AI 应用都要自己接工具。要接代码平台写一套，要接数据库写一套，要接本地文件写一套，要接企业系统再写一套。

这会变成大量重复胶水代码。

MCP 的意义在于，把“工具和上下文接入”推到协议层。

可以把它理解成：AI 应用不再单独认识每一个系统，而是通过统一规则发现工具、读取上下文、调用能力。

这对 Agent 很重要。

因为 Agent 的能力不只来自模型。它真正的能力，来自它能否连接真实世界：代码库、业务系统、文档、数据库、浏览器、文件系统、企业流程。

但是边界一定要讲清楚。

MCP 解决的是“怎么连得上”，不是自动解决“怎么用得安全”。

权限、审计、审批、隔离、速率限制、数据脱敏、工具误用，这些都还需要系统设计。

所以在演进史里，MCP 的位置是：

**它把工具接入从私有胶水推进到开放协议，但没有替你完成生产治理。**

这和前面的技能层正好互补。

技能回答的是：这类事情应该怎么做。  
工具协议回答的是：外部能力怎么标准化接进来。  
而下一层，多 Agent 回答的是：当任务太复杂时，多个角色怎么分工。

## 06. 多 Agent：不是多几个聊天窗口，而是责任分工


多 Agent，也可以直接叫“多智能体协作”。这条线可以看 AutoGen、CrewAI、AgentScope 这些代表。

AutoGen 早期更偏研究和实验，强调多个可对话 Agent 之间的协作。  
CrewAI 更强调角色、任务和流程，把团队和流程组织起来。  
AgentScope 也在多智能体、路由、交接、并发、记忆、技能这些方向上持续发展。

这条线为什么会出现？

因为很多复杂任务不是一个万能 Agent 能稳定完成的。

现实组织里也不是一个人做所有事。一个需求从提出到交付，可能要产品理解、技术设计、风险审核、测试验证、上线复盘。

所以多 Agent 的直觉很自然：既然真实世界靠角色协作，Agent 系统也可以模拟角色协作。

但它有一个特别大的坑：

**多 Agent 不等于更聪明。**

如果任务本身不清楚，输入输出不清楚，验收标准不清楚，把它拆成多个 Agent，只会让混乱多几个说话的人。

很多 Demo 看起来很热闹：一个规划，一个执行，一个审核，一个总结。可一到真实任务，就会互相重复、互相误导、互相放大幻觉，最后还没有明确责任人。

所以专业地看，多 Agent 不是能力增强器，而是组织结构。

组织结构的前提是边界清楚。

每个 Agent 应该知道：

我负责什么；  
我不负责什么；  
输入是什么；  
输出是什么；  
什么时候交接给别人；  
什么情况下必须让人确认；  
最终结果怎么验收。

这才是多 Agent 的核心。

如果没有这些边界，多 Agent 就只是把一个不可控循环，变成多个不可控循环。

至此，系统已经有了流程、状态、记忆、技能、工具协议、多角色协作。

但这些东西要长期运行，还缺最后一层：运行时和控制平面。

## 07. 运行时和控制平面：AgentOS 是趋势，不是某一家专属


走到这一步，Agent 技术开始从“开发框架”上移到“运行治理层”。

在这一阶段，会看到很多名字：Agno、AgentScope、Google ADK、OpenAI Agents SDK、LangGraph 生态、CrewAI 企业化路线。

这些项目的定位不完全相同，但它们都在靠近同一个问题：

**Agent 不只是要能写出来，还要能被运行、调度、追踪、评估、治理和管理。**

什么叫运行时？

可以理解成：让 Agent 不只是能被启动一次，而是能长期运行、调度、恢复、管理的执行层。

什么叫控制平面？

就是管理 Agent 系统的后台。比如查看运行记录，追踪工具调用，管理记忆和知识，配置权限，做人工审核，观察性能，跑评估。

AgentOS 这个词本身可能有营销色彩，但它指向的架构趋势是真实的。

当 Agent 从单次问答变成长期任务系统，就会需要：

运行时；  
任务调度；  
状态存储；  
记忆管理；  
工具权限；  
人工审核；  
追踪和日志；  
评估和回放；  
成本与性能控制；  
跨框架、跨模型、跨工具的统一管理。

Agno 可以作为这个趋势的一个样本。它强调构建、运行和管理 Agent 平台，强调追踪、调度、权限和控制平面。

但这不是 Agno 一家独有的方向。

AgentScope 在多智能体平台、运行管理、记忆、技能、MCP 等方向也有自己的体系。Google ADK 强调构建、调试、部署企业规模可靠 Agent。OpenAI Agents SDK 把工具、护栏、交接、会话、追踪这些能力放进官方开发套件。LangGraph 生态强调长任务、状态、检查点、人审和可恢复执行。

所以这一层真正值得关注的，不是某个名字本身，而是这个共同趋势：

**框架正在从写 Agent 的开发工具，上移为运行、治理和管理 Agent 系统的平台层。**

也正因为如此，只问“哪个框架最好”会越来越不够。

更有价值的问题是：

它解决的是开发层，还是运行层？  
它有没有状态恢复？  
有没有记忆治理？  
有没有技能沉淀？  
有没有工具边界？  
有没有追踪和评估？  
有没有人审和权限？  
有没有避免框架锁死的抽象？

当你这么问，整个 Agent 技术的发展就清楚了。

## 08. 为什么有些框架会消失，有些能力会留下


未来很多框架一定会消失，或者被吸收。

第一类，会被模型厂商吸收。

简单工具调用、基础交接、基础会话管理、基础追踪，OpenAI、Google、Anthropic、微软这些平台都会越来越内置。

第二类，会被云平台和企业基础设施吸收。

部署、调度、权限、审计、日志、监控、成本控制，这些本来就是基础设施擅长的事情。

第三类，会留下来，但留下来的不一定是今天的框架名字，而是它们抽象出来的工程责任。

比如：

LangGraph 这条线留下的是状态图、长任务、可恢复、可接管。  
MCP 这条线留下的是工具和数据接入协议化。  
Skills 这条线留下的是可复用能力包。  
AgentOS 这条线留下的是运行时、控制平面和治理。  
多 Agent 这条线留下的是角色分工、交接和组织结构。

所以框架名可以变，但底层问题不会变。

如果一个系统要长期成立，它必须回答这些问题：

任务怎么走？  
状态怎么存？  
记忆怎么治理？  
技能怎么沉淀？  
工具怎么授权？  
多角色怎么交接？  
运行怎么追踪？  
效果怎么评估？  
出错怎么回放？  
危险操作怎么隔离？

这就是这条演进线真正重要的地方。

## 09. 生产级 Agent 的 10 个坑


当 Agent 从演示走向生产，真正的分水岭不在功能列表，而在这些容易踩坑的地方。

第一个坑：把自动执行循环当完整架构。

自动循环只是起点，不是生产系统。没有状态、边界和评估，循环越强，风险越大。

第二个坑：状态只存在模型上下文里。

上下文不是可靠数据库。长任务必须有可恢复的状态存储。

第三个坑：把 RAG、记忆、知识库混成一坨。

知识库是资料入口，记忆是系统保留的信息，状态是任务进度，三者不能混用。

第四个坑：技能包只写成一段提示词。

真正的技能包应该包含步骤、模板、示例、工具、代码、边界和验收，不只是“请你按某种风格做”。

第五个坑：工具没有权限分级。

读文件、写文件、发消息、改数据库、执行命令行，风险级别完全不同，不能用同一个开关控制。

第六个坑：把 MCP 当成安全边界。

MCP 解决连接，不自动解决权限、审计、审批和隔离。

第七个坑：为了多 Agent 而多 Agent。

没有职责边界、交接规则和验收标准，多 Agent 只会制造更多噪音。

第八个坑：没有评估集。

不能只靠“看起来不错”判断 Agent 质量。至少要有典型任务、失败案例、对照输出和人工判分规则。

第九个坑：没有运行追踪。

没有追踪，就不知道错误来自模型、工具、检索、记忆、权限还是流程设计。

第十个坑：过早绑定框架，但没有沉淀业务技能。

框架换了以后，所有经验都丢了。真正应该沉淀的是流程、状态模型、工具边界、评估集和技能包。

这些坑其实都指向同一个结论：

**生产级 Agent 的难点，不是能不能跑一次，而是能不能被验证、回放、审计、纠错和持续改进。**

## 10. 结尾：框架会变，系统责任不会变


所以回到开头。

Agent 框架为什么一直变？

不是因为大家喜欢造新词，也不只是技术圈追热点。

更根本的原因是：大模型应用的责任边界在扩张。

当它只是聊天，提示词就够了。  
当它要连续行动，就需要自动循环。  
当它要稳定执行，就需要流程和状态。  
当它要理解上下文，就需要记忆和知识。  
当它要复用经验，就需要技能包。  
当它要连接真实系统，就需要工具协议和权限边界。  
当它要多个角色协作，就需要组织结构。  
当它要长期运行，就需要运行时和控制平面。

所以真正要讲的不是 Agno，也不是 LangGraph，也不是 CrewAI，也不是 AgentScope。

这些框架都是路标。

真正的主角是：

**大模型应用正在从“问答工具”，演化成“可运行、可管理、可治理的数字执行系统”。**

未来哪一个框架留下来，不容易下绝对结论。

但有几件事大概率会留下：

流程。  
状态。  
记忆。  
技能。  
工具边界。  
评估。  
追踪。  
运行治理。

看懂这些，再去看框架，就不会被名字带跑。

真正的问题不是“选哪个 Agent 框架”，而是：

**你的系统现在缺哪一层责任？**
