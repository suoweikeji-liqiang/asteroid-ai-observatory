> 专题线 `frontier_signal`，预计 8–10 分钟。  
> 核心锚点：一场题目、评分表和考场都可能变化的驾照考试。  
> 核心行囊：先审尺子，再量模型；排行榜负责筛选，真实任务负责决定。

## 钩子

八个月，AI 编程模型在一套公开测试上的通过率，从百分之二十三点三，冲到了百分之八十点三。

看起来，模型能力发生了一次大爆炸。

可就在七月八号，OpenAI 突然发文说：这套测试里，大约三成题目可能是坏的。然后，他们撤回了自己此前的推荐。

问题来了。

如果卷子本身有错，百分之八十这个漂亮分数，到底在量什么？

## 第一段｜出题人把自己推荐的卷子否了

这组数字，来自二零二六年七月八日，OpenAI 在官网发布的一篇研究文章。发布机构和作者署名都是 OpenAI，原文标题叫《Separating Signal from Noise in Coding Evaluations》，中文可以翻成《从代码评测中分离信号与噪声》。

这套测试叫 SWE-Bench Pro。

它想测的事情很接近真实开发：给 AI 一个 GitHub 问题和一份代码，让它自己读项目、修改代码，最后跑隐藏测试。测试过了，就算修好了。

你可以把它想成一场 AI 的驾照考试。

模型是考生，代码库是考试车辆，GitHub 问题是题面，隐藏测试就是考官手里的评分表。

它比那种问一道算法题、让模型当场写答案的测试真实得多。

二零二六年二月二十三日，OpenAI 在官网发布《Why SWE-bench Verified No Longer Measures Frontier Coding Capabilities》，中文是《为什么 SWE-Bench Verified 已经无法衡量前沿编程能力》。那篇文章认为，上一套常用测试 SWE-Bench Verified 已经被污染、也有不少坏题，公开建议行业改用 Pro。

结果五个月后，OpenAI 又把 Pro 审了一遍。

他们先用自动管线检查题目、模型的尝试记录、失败轨迹和任务元数据，筛出可疑题；再让调查 Agent 多轮检查；同时请有经验的软件工程师独立复核。

最后得到两个数字。

自动分析路径认为，七百三十一道公开题里，有二百道存在会破坏评测的问题，占百分之二十七点四。

人工复核路径认为，有二百四十九道，占百分之三十四点一。

所以 OpenAI 给出的估计是：大约三成任务有问题。

注意，这里说的是 SWE-Bench Pro，不是所有 AI 榜单都有三成坏题。这个边界必须说清楚。

但哪怕只是一套榜单，三成也足以把排名搅乱。

## 第二段｜四种坏题，能把对的判错，也能把错的判对

OpenAI 把问题分成四类。

第一类，考官偷偷指定了动作。

题目只要求你把车停进车位，但评分表要求你必须先向左打一圈半、再向右两圈。你用另一种方法停得又正又稳，照样零分。

放到代码里，就是测试强制某个函数名、某种结构、甚至某个字符串格式，而这些要求根本没有写在题目里。

第二类，考官漏念了要求。

题面只说靠边停车，隐藏评分却还要求你拉手刹、关灯、车轮回正。不是这些动作不重要，而是你不能不告诉考生，又拿它们判生死。

第三类，监控有盲区。

模型其实只修了一半，但测试没有覆盖剩下那一半，于是错误方案也能过关。

第四类更麻烦：题目本身把人往错误方向带，甚至和隐藏测试互相矛盾。

OpenAI 给了一个很小、但特别有杀伤力的例子。

有道题要求模型把目录条目重新输出成 Markdown。题目给的示例，竖线前是一个空格；隐藏测试要的，却是两个空格。

模型老老实实照题面做，只因为少了一个题目从没要求过的空格，就被判失败。

这种题最危险的地方，不只是冤枉一个模型。

它会让所有人对着总分做决定：谁第一，谁退步了，哪个模型值得全公司切换。一个小小的评分错误，最后可能被放大成采购、研发路线甚至安全判断。

而反过来，覆盖不足的测试又会把没修好的代码判成通过。

所以坏题既能制造假失败，也能制造假成功。

分数写得越精确，我们反而越容易忘记：小数点后那一位，可能建立在一把弯掉的尺子上。

## 第三段｜为什么换一套新题，问题还会回来

这件事不能简单归结为谁工作不认真。

根上的难题是：很多 Coding Benchmark 的题目，来自真实 GitHub 仓库的 issue、PR 和测试。

可 GitHub 上的一次真实开发，从来不是一张干净试卷。

一个问题可能在评论区来回讨论十几轮；真正需求散落在 issue、代码、评审意见和发布说明里；最后那组测试，往往是为了验证某个具体补丁写的，不是为了定义世界上所有正确解法。

现在把这段长期协作历史切出来，只留一段题目、一份旧代码和一组隐藏测试，很多原本依赖上下文才能成立的条件，就丢了。

更麻烦的是，这些仓库、问题和正确补丁大多公开存在。

这就像驾校把往年考题和标准路线一起挂在网上。模型不一定真的背过答案，但只要训练数据里见过相关代码、发布说明或者补丁，它的高分里就可能混进“见过题”的成分。

这也是为什么 OpenAI 今年二月先停用 Verified，推荐 Pro；到了七月，又撤回对 Pro 的推荐。

坏的未必是某一张卷子。真正难的是，我们总想把复杂的软件工程能力，压成一个干净、稳定、还能长期使用的总分。

## 第四段｜就算卷子没坏，它也未必在测你的工作

我们再退一步。

假设这套公开题库已经完全干净，每道题都公平，测试也没有漏洞。排行榜是不是就能直接替公司选模型了？

还是不能。

二零二六年七月一日，Microsoft for Developers 发布了一篇工程文章，作者是微软首席开发者倡导者 Waldek Mastykarz。原文标题叫《What AI Benchmarks Are Not Telling You》，中文是《AI Benchmark 没告诉你的事》。

这篇文章提醒了第二个问题：公开榜单测的，通常是热门开源仓库里的公开问题。

可你公司的真实任务，可能是另一种世界。

模型没见过的私有 SDK、团队自己的代码规范、几十个工作区扩展、AGENTS.md、MCP 工具、内部认证库，还有一个会不断报错、让 Agent 反复修正的真实开发环境。

公开榜单里的高分，只能说明这个模型在那套题、那辆车、那个考场里表现不错。

它不能自动证明，模型进了你公司的地下车库，也一样会开。

这不是说高分模型一定不好。

更准确的说法是：你还不知道。因为榜单没有测你的任务。

所以公开 Benchmark 最合理的角色，是初筛。

一个模型只有百分之三十，可能说明基础能力确实不够；一个模型有百分之九十，说明它值得进入下一轮。但最后选谁，不能只靠这张成绩单。

## 第五段｜连考场天气都会偷偷改分

第三个问题，更容易被忽略：你以为自己在测模型，其实还在测模型周围的一整套环境。

二零二六年七月八日，Waldek Mastykarz 又在 Microsoft for Developers 发布了《The Hidden Variables in Your Agent Eval》，中文是《Agent 评测里的隐藏变量》。

文章记录了同样提示词在不同系统上的对比。

在 Windows，Agent 更可能使用 PowerShell；在 Linux 和 macOS，它更熟悉 Bash 或 Zsh。Shell 一变，命令怎么写、错误怎么恢复、后面每一步怎么走，都会跟着变。

语言服务器，也就是平时在编辑器里给代码画红线、报类型错误的那套东西，有没有开启，也会改结果。

有它，Agent 可能在生成代码的同一轮就发现错误、当场修正。没有它，错误要等到构建失败后才暴露，可能多花几轮，甚至一路错下去。

连文件路径都可能带偏模型。

一个叫 `/workspace/project` 的中性目录，和一个带着 `azureuser`、`test-workspace`、`poc-api` 的路径，会给模型完全不同的暗示。

模型没换，题目没换，只是操作系统、Harness、LSP 或路径变了，分数就可能变化。

Microsoft 在文章里甚至提醒：一次看起来提升八分的模型切换，可能完全被换了一台机器解释。

这时候你比较的，已经不是两个模型。

是两名考生，开着不同的车，在不同天气、不同路线、不同考官手里跑出来的两个成绩。

## 第六段｜排行榜别扔，但要把它降级

那普通团队是不是要自己造一套几百题的大榜单？

不需要。

真正有用的是三层测量。

第一层，公开榜单负责筛选。

它能帮你快速排除明显不够用的模型，判断大概处在哪个能力档位。但别拿五分、三分的差距，直接做采购结论。

第二层，用自己的真实任务决定。

从团队每天真的会做的事情里，先挑三到五个场景：改一个常见功能、接一套私有 SDK、修一个历史故障、遵守你们自己的代码和安全规范。

同样的任务、同样的工具、同样的环境，让候选模型分别跑。看最终结果，也看花了多少轮、是否稳定。

二零二六年七月八日，Databricks 工程博客发布了《Benchmarking Coding Agents on Databricks' Multi-Million Line Codebase》，中文是《在 Databricks 数百万行代码库上评测 Coding Agent》。

这篇文章由 Vinay Gaba、Ankit Mathur、Rishabh Singh、Patrick Wendell 和 Matei Zaharia 联合署名。Databricks 就是这么做的。

他们用内部真实工程任务做私有评测，用保留测试检查最终代码，而不是只让另一个大模型判断“看起来像不像对”。

但连他们早期也踩过一个坑：有些 Agent 成绩好得不正常。人工读轨迹才发现，Agent 能从 Git 历史里直接找回当年的正确实现。

后来，他们把运行期间的 Git 历史封掉了。

这件事特别说明问题：私有题库也不是天然可信。题目得审，答案得防泄漏，异常高分得回看轨迹。

第三层，固定考场。

每次记录模型版本、Harness 版本、操作系统、工具和 LSP；使用不带暗示的路径；同一个场景多跑几次。

这套具体建议，来自二零二六年七月十五日，Waldek Mastykarz 在 Microsoft for Developers 发布的系列收官文章《Building AX Evals That Actually Work》，中文是《构建真正有效的 AX 评测》。

文章给出的起步方法很朴素：三到五个真实场景，每种条件先跑五次。分数一致，说明信号比较清楚；结果三比二，就先别急着宣布谁赢了。

## 诚实补丁｜公开 Benchmark 仍然有用

说到这里，别走到另一个极端。

公开 Benchmark 不是骗局，也不是完全没用。

它仍然能告诉我们一个模型有没有基础编码能力，能不能处理跨文件修改，也能在条件固定时帮助观察明显退步。

真正不靠谱的，是把一场陌生考场的总分，直接当成自己公司的试用期结果。

尤其当模型已经逼近题库上限，坏题、污染、任务分布和环境变量占掉的信号会越来越大。这个时候，排行榜每涨一分，不一定都对应现实能力涨了一分。

## 收束｜下次看到新榜单，先问三句话

以后再看到某个新模型“榜单暴涨”，先别急着换。

先问三句话：

第一，这把尺子坏没坏？题面、测试和正确答案对得上吗？

第二，它量的是不是我的工作？公开题和我的真实任务有多大重叠？

第三，考场有没有变？模型之外的 Harness、工具和环境固定了吗？

这期如果只记住一句话：

**先审尺子，再量模型；排行榜负责筛选，真实任务负责决定。**

下一期，我们顺着这条线继续拆一个更反常识的问题：为什么每百万 Token 更便宜的模型，做完一件事反而可能更贵。

如果你正在给团队选 Coding Agent，也可以把你最想拿来实测的真实任务留在评论区。别报模型名字，先报任务。任务比站队更有价值。
