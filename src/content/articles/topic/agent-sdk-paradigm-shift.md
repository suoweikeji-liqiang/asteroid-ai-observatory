> 核心判断：工具、检索和基础执行循环正在被官方 SDK 商品化，团队的差异化随之上移到 Skills、上下文、策略边界和业务评测。框架没有消失，但应该在确实需要多供应商、复杂编排、强类型或更深可观测性时再引入。


---

## 01. 开场

十二个月前，搭一个 AI agent，几乎是一套固定动作：挑一个框架，定义一堆工具，搭一条 RAG 管线，再写一摞胶水代码把它们接起来。这是当时的默认剧本。但很多团队复盘半年下来，结论都一样：一半的时间，花在了和 agent 本职工作毫无关系的基础设施上。


---

## 02. 现在，活儿不在那儿了

而到了二零二六，活儿已经不在那一层了。中间那一层，大半没了。SDK 自带了工具，skills 系统取代了开工前那张工具注册表，更长的上下文窗口，把向量检索从它霸占了一整年的默认位置上挤了下去。


---

## 03. 核心判断 · 问题上移了一层

这其实是基础设施变迁里反复出现的老剧本：难的东西变便宜了，便宜的东西成了标配，问题，就往上移了一层。所以这期讲的，不是某个新框架，而是：搭 agent 这件事，到底是哪一层被吃掉了，团队真正该花力气的，又变成了什么。


---

## 04. 第一部分 · 老套路：八成是胶水

先看看被取代的那套老套路，长什么样。


---

## 05. 二四到二五年的标准动作

二零二四到二五年，一个 agent 项目通常是这样：先挑一个框架。然后写工具定义，基本是给某个接口包一层壳。再搭一条检索管线：把文档切块、做向量、挑一个向量库、写检索器，上面再叠一层重排。最后，agent 主循环还得自己写——拼提示、分发工具、重试逻辑、可观测性，全都要管。


---

## 06. 当年这么干，是有理由的

当年这么干，是有充分理由的。那时的基础模型上下文窗口短，不自带文件访问，也不能跑代码。你要让 agent 拿你的数据干点正事，就只能把数据预先嚼碎成小块，喂到模型嘴边。但代价不只是搭建时间，还有基础设施账单、对着 embedding 接口的反复重试，以及一套随着模型变强、反而越来越拧巴的上下文策略。


---

## 07. 检索层，成了质量瓶颈

到二零二五年中，检索层常常成了质量的瓶颈。agent 问一个问题，拿回五段看起来都挺像样的片段，然后就从这五段里作答，而不去读你真正想让它读的那份文档。三月某个周二拍脑袋定的切块方案，半年后还在拖累答案质量。用原文作者的话说：二零二五年我聊过的大多数团队，都在调他们的 RAG 管线；几乎没人，享受这件事。


---

## 08. 第二部分 · 三件事，一起塌了中间层

那中间层是怎么塌的？是三件事，几乎同时落地，把它一起压垮了。


---

## 09. 变化一 · 工具，SDK 自带了

第一件，内置工具。Claude 的 Agent SDK，开箱就带好了一整套：读写文件、编辑、跑命令行、全文搜索、抓网页；OpenAI 的 Codex SDK 形态也类似，默认给 agent 配好了命令行和文件工具。这些，正是二零二四年每个 agent 项目都在重造的轮子——一个能处理大文件的读取，一个会流式输出、还守着工作目录的命令行，一个不会被大文件噎住的搜索。当年八成要团队重新实现的工具，现在成了标配。十行配置，就能让 agent 干真活。


---

## 10. 于是，差异化上移了

但这有个翻面：差异化上移了一层。价值不再在于"你有没有 Read 这个工具"，而在于"agent 拿着它，到底做了什么"。人人都有的能力，不再是你的护城河。


---

## 11. 变化二 · MCP 之外，CLI 回来了

第二件，工具箱以外的能力，通过 MCP server 接入；它的注册表从二五年初到现在涨了近八倍，主流模型厂商也都上了首方支持。但二零二六的图景更分层了：很多原来要起一个 MCP server 的活，现在让 agent 直接通过 Bash 调一个命令行工具、再把这套配方包成一个 skill，反而更好。基准测试显示，命令行工具调用的上下文成本，只是等价 MCP 调用的零头，往返更少、出错的方式也更少。MCP 仍然守得住它的地盘——浏览器控制、OAuth 流程、流式服务这类协议重的活；但它，不再是"怎么给 agent 加个新能力"的那个自动答案了。


---

## 12. 变化三 · skills 取代了"堆工具"

第三件，skills 取代了堆工具。老办法是开工时就把 agent 可能用到的每个工具都注册上，不管这一轮用不用，每一轮都吃一份上下文——一百个工具，意味着 agent 还没开始想问题，系统提示就已经很沉了。skills 把这个翻了过来：一个 skill，就是一个带名字和一行描述的小 markdown 包。agent 平时只看那行描述，大概一百个 token，只有当它判断这个 skill 相关时，才把正文加载进来。Anthropic 把这叫渐进式披露——因为正文按需才加载，一个 skill 里能塞的内容，几乎没有上限。


---

## 13. 变化四 · RAG，被降级了

第四件，也是冲击面最大、却最少人讨论的一件：RAG 被降级了。一年前，只要有人问"agent 怎么处理一大堆文档"，反射性的答案就是"上 RAG"。今天，这个问题分成了三岔路：语料能塞进上下文窗口，就直接塞进去；agent 能在文件系统里搜，就让它自己搜；只有当语料确实大到这两条路都走不通，向量检索才仍然是对的——而你会发现，这类情况比以前少多了。看今天的编码 agent 就知道：它们靠的是文件搜索和直接读文件，多过靠向量检索。


---

## 14. 不是向量检索变差了

说清楚一点：不是向量检索变差了。是它周围的上下文，改善到了一个程度，让它不再是你的第一选择。同一个工具，环境变了，它的位置就变了。


---

## 15. 那么，留给团队的是什么

三件事合起来，被拉进 SDK 的，正是一个 agent 项目的"中间"：工具层、检索层、还有那个主循环。那留给团队的是什么？是系统提示、是 skills、是围绕"这个 agent 被允许做什么"的那套策略。换句话说，省下来的力气，该花在判断和边界上，而不是再去造一遍轮子。


---

## 16. 第三部分 · 那还需要框架吗

讲到这，很多人第一反应是：那框架是不是没用了？没有。但你伸手去拿框架的场景，确实变窄了。


---

## 17. 框架没死，只是场景窄了

框架各有各的不可替代。Pydantic AI，适合你要强类型、确定的输出结构、还有一套和你 Python 代码库思路一致的评估循环。LangGraph，适合你的问题本质上就是一张带分支和人工审批的 agent 状态图。OpenAI 的 Agents SDK，围绕 agent 之间显式的交接来设计，这个模式合你的拆分方式，它就值。CrewAI，是原型一个多 agent 系统最快的路，只要你受得了它的那套主见。


---

## 18. 什么时候算"长大了"

作者给了个心智模型：从 SDK 起步，等你长大到 SDK 装不下了，再去拿框架。而"长大"，通常是这四件事之一。第一，多供应商路由：你的生产流量跑在不止一个模型厂商上，需要官方 SDK 不给的那层路由。第二，多 agent 编排：你的问题真的拆成了带交接、分支、人工审批的几个 agent。第三，确定性类型：你需要围绕输入输出的强 schema 和校验。第四，生产级可观测性：你要的评估、回放、追踪，超出了 SDK 自带的范围。


---

## 19. 四个都没咬你，SDK 就够

反过来说，如果这四件事没有一件正在咬你，那 SDK 大概率就够了。在它上面再叠一层框架，会是你六个月后会后悔的一层。先用最简单的东西，等问题真的逼你了，再加复杂度——这一点，Anthropic 自己讲怎么搭有效 agent 的文章，落点也在同一处。


---

## 20. 第四部分 · 落到你自己的盘子里

这套新形态，有两点能很干净地映射到工程和内容的活儿上。


---

## 21. 启发一 · 自带工具 + 受治理的动作

第一点：内置工具，加上受治理的动作，这正是一个基础设施平台早就在跑的模型。SDK 假设 agent 手里有能干真活的工具；而平台假设，这些工具外面套着策略、审计日志和短期凭证。这两套假设，是叠在一起的。能力放开的同时，边界和留痕必须跟上——这跟我们前面讲 Agent 安全、讲上线门禁，是同一条线。


---

## 22. 启发二 · 结构化的上下文，不用切块

第二点：一张结构化的状态图，本身就是上下文，你不用切块、也不用做向量。一个在你代码库或配置图上推理的 agent，可以像 grep 代码一样 grep 这张图，而答案，就 grounded 在你整个平台共用的同一个事实源上。这也回到这期的主线：能让 agent 直接读到可信、结构化的上下文，就别再退回去切块、嵌入、调检索。


---

## 23. 第五部分 · 结论

所以把这一整期，收成一句话。


---

## 24. 一年前八成胶水，今天反过来

一年前，一个 agent 项目，八成是胶水代码，两成才是 agent 真正要做的事。今天在大多数项目上，这个比例反过来了。被吃掉的，是工具、检索和循环这些中间件；留下来的，是判断、是 skills、是策略——是只有你才定得了的那部分。


---

## 25. 先用 SDK 的方式搭

所以如果你手上压着一个 agent 的想法，作者的建议很直接：先用 SDK 的方式把它搭出来，只有当你撞到 SDK 确实做不了的事，再去伸手拿框架。大多数团队会惊讶地发现：那种时候，远比想象中少。


---

## 26. 把省下的力气，花在对的地方

这对我们做内容线、做工具链同样成立。中间层被商品化之后，真正拉开差距的，不再是你又造了一套工具，而是你给 agent 配了什么样的提示、什么样的技能、什么样的边界，以及你让它读到的，是不是可信、结构化、能追溯的上下文。省下来的力气，要花在这些只有你能决定的地方。
