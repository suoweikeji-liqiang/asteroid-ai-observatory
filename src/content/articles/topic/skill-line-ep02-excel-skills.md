让 AI 清洗一张表并不难。难的是把本次处理固化成脚本，下个月换一批数据后，仍能保留同样的冲突判断、审计记录和错误提示。

我们在 2026 年 7 月比较了三个可直接交给编码 Agent 使用的轻量技能：Anthropic 官方 `xlsx`、OneWave AI 的 `csv-excel-merger`，以及 Jeremy Longshore 技能集合中的 `excel-macro-creator` 系列。测试分三层：合并字段不一致的区域表、清理日期与金额等脏数据、把流程固化后用全新数据重新验收。

## 为什么“新数据回归”比第一次成品更重要

测试数据故意放入一组陷阱：两条记录拥有相同订单号，但客户不同。它们不是普通重复项，自动删除其中一条会造成真实数据损失。

三个候选在交互式任务中大多能识别这个冲突。问题出现在固化脚本后：两个候选退化成仅按订单号覆盖，模型在聊天时表现出的判断力没有进入代码。也就是说，第一次结果看起来正确，不能证明自动化流程可复用。

这也是表格自动化最危险的失败方式：脚本正常退出、文件成功生成、工作簿也能打开，但业务语义已经悄悄丢失。

## 三个候选的实测观察

### Anthropic `xlsx`：规则完整，适合作为工程基线

官方 skill 当前明确区分 `openpyxl`、`pandas` 和快速读取工具的用途，还要求公式重算、零公式错误、保留既有格式并记录假设。它不是“帮你写几个单元格”的提示词，而是一份围绕工作簿交付的检查清单。

在我们的测试快照中，它的字段映射和冲突识别最规矩：有争议的记录进入独立工作表，没有擅自替用户决定。但它生成的复用脚本没有完整保留这套判断，并且文字说明与代码行为存在偏差。官方 skill 此后已经更新，因此这个故障应理解为当次生成结果的问题，而不是对当前版本的永久判断。

### `csv-excel-merger`：合并专精，但仍要审代码

这个技能对合并策略、冲突处理和验证断言写得较具体。首次任务中，它对缺失值采取保守处理，也会显眼标注冲突。但回归任务里，固化脚本依然把复杂冲突简化成机械去重，说明“文档里有策略”不等于“生成代码一定实现策略”。

### `excel-macro-creator` 系列：文档薄，样本代码反而最好

测试时，这组技能的说明更像通用模板，缺少针对 Excel 场景的具体代码路径。意外的是，它生成的脚本却是唯一保留“订单号相同但客户不同”分支的候选，并在日志中说明保留与丢弃的记录。

这不是说说明文档不重要，而是提醒我们：不能用 README 的厚度替代产物验收。技能质量、模型执行和具体任务之间存在交互，必须看最终代码和回归结果。

## 一份可复用表格流程至少要验什么

1. **先定义业务主键。** “订单号相同”是否必然代表重复，必须由业务规则回答。
2. **冲突与重复分开处理。** 真重复可以合并；字段矛盾应进入人工复核表，不能静默覆盖。
3. **新数据必须包含反例。** 不要只用原数据再跑一遍，要加入新列、空值、格式变化和主键冲突。
4. **检查代码，不只检查文件。** 确认日志中声称的警告确实存在于分支逻辑里。
5. **公式要重算并验证语义。** 文件无报错只能证明公式可计算，不能证明引用范围正确。
6. **保留审计轨迹。** 输出行数、被删除记录、冲突记录和假设应写入日志或独立工作表。

如果任务只执行一次，三个候选都能提供帮助；如果流程每周或每月复用，真正的交付物不是那份 `.xlsx`，而是“脚本 + 测试数据 + 审计记录”。
